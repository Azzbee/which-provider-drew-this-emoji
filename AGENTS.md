## Rules for the paper

1. **Every number must come from a saved file.** Verified numbers come from `codebase/outputs/` or `codebase/report/numbers.json`; Kaggle scores from the competition's submissions page. If you cannot point to the file, the number does not go in. If something is unknown, write that it is unknown.
2. **Keep the tags.** `\ver` marks numbers the codebase reproduces; `\rep` marks numbers from the team log or Kaggle that the codebase does not reproduce. A new number from your own notebook is `\rep` unless its code and outputs are committed under `codebase/`.
3. **No em dashes** anywhere (use commas, colons or full stops). En dashes in ranges like `97.47--97.87` are fine.
4. **Do not change the final-model numbers** (97.69% OOF, 0.98218 private, 0.98238 team best, 5th of 18) without a new verified run.
5. Figures are regenerated with `python paper/make_figures.py`; never paste numbers into a figure by hand.
6. Build before you push: `cd paper && make` must finish with no `!` errors and no `undefined` references (check `main.log`).
7. The section order follows the teacher's brief: front page; abstract, contents, model chosen; preprocessing; architecture; metrics; performance; AI and code; conclusion. Keep it.

## Rules for code and data

- Never commit the competition data (`codebase/data/extracted/`), caches, checkpoints larger than a few MB, API keys or `kaggle.json`. `.gitignore` covers the usual cases; check `git status` before committing.
- To rerun anything, extract the Kaggle archive into `codebase/data/extracted/` (see `codebase/README.md`).
- Python 3.13, versions pinned in `codebase/requirements.txt`. Tests: `python -m pytest codebase/tests -q`.

## Adding your method

1. Put it in `members/<your-name>/`: a short `README.md` (model, input size, preprocessing, training settings, validation protocol, score, Kaggle file name) plus the notebook or script.
2. If it should appear in the paper, add a row to `paper/parts/who.tex` and, if it changed the direction of the project, to the journey table in `paper/parts/journey.tex`.
3. Commit with a message that says what you added, then push (see below).

## Git workflow

```bash
git pull --rebase            # always before you start and before you push
# edit, then build the paper
git add -A && git status     # check nothing large or secret is staged
git commit -m "paper: add DINOv2 settings to section 4.4"
git push
```

Small, frequent commits with clear messages. Commit dates must be the real ones; do not rewrite history.
